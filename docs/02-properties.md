# 2. Property reference

Every device property this record has evidence for. Values are 2-byte little-endian unless the type column says otherwise. "Per bank" properties hold the contents of the bank currently selected with `0xD18C`; the others describe the camera as a whole.

Nearby codes advertised by the X-T50, with the names other projects give them: `0xD184` IOPCode, `0xD186` TetherRawConditionCode, and `0xD187` TetherRawCompatibilityCode [Published: libgphoto2]. `0xD184` answers a string of two comma-separated 8-character codes, the first of them the conversion profile's IOPCode: `FF189504,FA189504` on an X-T50 fw 1.31 [Published: FilmKit issue #12 log] and `FF179501,FA179501` on an X-H2 [Published: fujifilm-ptp-recipes]. `0xD186` and `0xD187` answer a model string: `X-T50_0100` on an X-T50 at fw 1.31 [Published: FilmKit issue #12 log] and at fw 1.32 [Measured: X-T50 fw 1.32, 2026-10-15], `X-H2_0200` on an X-H2 that fujifilm-ptp-recipes gives as fw 5.20 in one place and fw 2.00 in three [Published: fujifilm-ptp-recipes], so the suffix isn't the firmware version. That project's static analysis of X RAW Studio finds that the string is the key into the application's per-model capability table, read once per session; the camera states an identity and the PC decides what to allow. Its [call-chain account](https://github.com/ILFforever/fujifilm-ptp-recipes/blob/daba2d97d6b37bd1d5dbc68ca974f6b22f433071/docs/reverse-engineering/xraw-studio-call-chain.md#L93-L99) says older bodies fail the `0xD186` read with SDK error `0x1005`, and that X RAW Studio then builds the key as the model name plus `_0100`; it lists no bodies. [Published: fujifilm-ptp-recipes, static analysis] None of them is needed for anything in this record.

"Recipe setting" marks the properties that make up a film simulation recipe. The rest are bank settings that a recipe tool should carry through unchanged. fujifilm-ptp-recipes writes `0xD190`–`0xD1A2` only and treats `0xD18E`, `0xD18F`, `0xD1A3`, and `0xD1A4` as read-and-log [Published: fujifilm-ptp-recipes]; fuji-ptp-notes never writes `0xD1A4` [Published: fuji-ptp-notes].

The bank block and the camera's live state are separate stores. On an X-H2 with C7 selected, `0xD192` read `12` (ACROS) while the live `0xD001` read `4` (PRO Neg. Hi). [Published: X-H2 fw 5.20, fujifilm-ptp-recipes]

A bank also stores settings that aren't among these 23. X RAW Studio lists Sports Finder Mode, Digital Tele-Converter, and HDR among a bank's contents. ISO is also stored per bank, and so is the JPEG/HEIF file format: with one bank on HEIF and another on JPEG, Clarity was refused on the first and accepted on the second in the same session [Measured: X-T50 fw 1.32, 2026-10-15]. Exposure compensation isn't per bank on the X100VI, which ties it to its dial [Community: FilmKit issue #6]; the same report asserts, without a test, that it's per bank on bodies without a dial, such as the X-H2. The camera's **AUTO UPDATE CUSTOM SETTING** item decides whether a change made on the body lands in the current bank at once or is only marked for saving [Published: Fujifilm manuals, X-T50]; see [custom banks](04-custom-slots.md#writing-a-bank). None of them is readable through this block, but they change which writes the camera accepts; see [Why a write is refused](04-custom-slots.md#why-a-write-is-refused).

## Live shooting properties

These describe what the camera is using right now, not what a bank stores. Live writes are outside this record's scope, but X RAW Studio's bank save shows what the codes mean.

The captured combined save writes the bank and then mirrors the recipe to the live properties. In the FilmKit #12 capture, after the name and 23 bank-setting writes `0xD18E`…`0xD1A4`, the first live command follows the last bank-setting command by 85 ms. The 23 live writes carry the value just written to each bank property, in the bank write's own order (`0x5005`, `0xD017`, `0xD00B`, `0xD00C` for the white balance group). They answer in 4–18 ms. Accepted bank-setting writes took 55–246 ms; three bank refusals took about 46 ms, while the Kelvin refusal took 5.283 ms. The camera accepted the four live writes whose bank twins it refused. The first live write is `0xD1A5`. [Captured: X-T50 fw 1.31, FilmKit #12 capture] For the full sequence, see the [editor-walk transcript](../captures/x-rawstudio-editor-walk-xt50-xt30.md). The live write is optional in X RAW Studio: its **Copy to CAMERA** dialog has a **CAMERA SETTING** box for it beside the **CAMERA CUSTOM SETTING** box for the bank, and a 16-bit selector carries both choices. [Published: fujifilm-ptp-recipes, static analysis] Both peer records map matching bank/live address pairs and describe each pair as sharing its encoding: fujifilm-ptp-recipes all 23, fuji-ptp-notes 20 (none for `0xD18E`, `0xD18F`, or `0xD1A3`). This does not mean their enum tables agree with each other; the DR Auto and film-simulation disagreements remain in [errata](errata.md). Separately, the X-H2 is reported to read all 23 live codes, but the source conflicts about live write coverage: its verification page says all 23 were written, while its status page says live Lens Modulation Optimizer was never written. See [the coverage qualification](01-transport.md#the-advertised-lists-are-not-complete). The GFX100RF source reports live writes from macOS and iOS in **USB TETHER SHOOTING** mode without enumerating exactly which codes were written. [Published: X-H2 fw 5.20, fujifilm-ptp-recipes] [Published: GFX100RF, fuji-ptp-notes]
